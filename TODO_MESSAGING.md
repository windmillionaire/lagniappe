# Deferred Messaging and Notification Integration

**Status:** Post-initial-release TODO  
**Last updated:** 2026-08-14

This document is an implementation plan, not a commitment to include messaging
in the initial release. The goal is a small asynchronous communication feature
that works with Lagniappe's existing Notifications, permissions, task, search,
and collaborative-document systems. It must not become a realtime chat product.

## 1. Goals and boundaries

The first messaging release should provide:

- one-to-one plain-text messages between eligible managed users;
- a centralized Messages page with durable, cursor-paged peer history;
- one aggregate message row in Notifications rather than one notification row
  per message;
- ordinary Notifications when a task is newly assigned to another user;
- `@` mentions in Page and Project collaborative documents, delivered only
  after a durable document checkpoint;
- two owner-controlled inbound exceptions for an owner who otherwise sits
  outside normal groups;
- exact notification counts without loading message history when the
  Notifications menu opens.

The first version does **not** include realtime delivery, a chat-style inline
composer, typing/presence, attachments, subjects, group messages, message
editing, email/push delivery, connection requests, or read/delivery receipts
beyond the unread count. It also does not add owner/admin access to other
users' message bodies.

Public users retain operational Notifications already generated by the app,
but cannot send, receive, search for, or be assigned through these collaboration
features.

## 2. Relevant current architecture

The implementation should extend existing mechanisms rather than create a
parallel permission or refresh system.

- `Notification` is an `activity` entity parented by a User. The menu currently
  loads through `GET /l/notifications`, and individual/delete-all operations
  remove durable Notification rows.
- `lagniappe/core/tools/cache/notifications.py` maintains a rebuildable Redis
  generation/revision/membership projection. Browser state is carried in
  `X-Lagniappe-Notification-State`; the menu itself remains lazy.
- The current Notifications menu performs one keys-only ancestor query and
  then batch-hydrates rows and direct relations. Preserve the one-query
  property while bounding the result set.
- Cached facet search already combines a requested restriction set with the
  current user's `belongs_to` hashes. `permission=assign` is the model for a
  purpose-specific user selector.
- Public users are not present in the searchable user cache. Preserve and test
  that invariant; do not add a redundant public-user facet filter. Mutation
  endpoints must still reject a directly submitted public-user key.
- Task assignment currently uses `user_assign_restrictions` in its selector.
  The submitted `assigned_to` key is hydrated by the task route, so the future
  work must add a matching commit-time restriction check.
- Page and Project documents are Tiptap/Yjs documents. `POST /l/sync` persists
  HTML only when a checkpoint is accepted, and its offline queue already owns
  replay of document changes. Mentions must attach to that boundary.

## 3. Permission model

### 3.1 Direct messages

Add a cached `user_message_restrictions` value alongside the existing search
and assignment restrictions.

For a managed sender, the eligible group hashes are the union of:

- non-public groups the sender belongs to; and
- groups on which the sender's permission implies `VIEW`.

Global Users `VIEW` makes the restriction unrestricted. The owner may message
any managed non-public user. Self-messaging is excluded.

Expose this through the existing user facet endpoint as
`permission=message`. Do not build a second user directory or load group
entities for each query. The cache result is the authorization-filtered
suggestion set.

The send endpoint must apply the same current restriction predicate to the
submitted recipient. This is not a second group lookup: it compares the loaded
recipient's required hashes with the current cached restriction state. It
prevents a hand-written request from bypassing a selector the client never
opened and rejects missing, deleted, public, or self recipients.

If eligibility is later lost, both participants retain their existing history,
but the UI disables compose and the server rejects new sends.

### 3.2 Owner exceptions

Add two optional booleans to the owner User record:

- `allow_messages_and_mentions`
- `allow_task_assignments`

Missing values resolve to `false`, so no data migration is needed for these
fields. Only the owner may change them, in the owner's own **User Data** panel.
The settings govern inbound collaboration; they do not limit what the owner
may send or assign.

Maintain a small shared Redis projection containing the owner key, display
name, normalized searchable name, both toggles, and a revision. Update it when
the owner's name or either setting changes, memoize it per request, and lazily
repair it from the canonical User row on a cache miss. Do not copy these
settings into runtime config and do not load the owner entity on every route.

Owner handling in user searches is deliberately special:

1. Remove/deduplicate the owner from ordinary cached results, including an
   otherwise unrestricted result set.
2. Normalize the non-empty query and owner name consistently.
3. Append the owner only if the applicable toggle is enabled **and** the full
   normalized query occurs somewhere in the normalized owner name,
   case-insensitively.
4. Never append the owner for an empty or nonmatching query.

This rule applies to message, mention, and assignment suggestions, using the
appropriate toggle. An already selected owner may still be rendered as a
preloaded assignee or historical peer without matching a new search; preloads
are display state, not suggestions.

At mutation time the recipient/assignee owner row is already being loaded. Use
its canonical toggle for the final check so a stale shared projection cannot
grant access.

### 3.3 Mentions and assignment

Mention eligibility starts with the direct-message restriction, then also
requires the recipient to be able to `VIEW` the referenced document. The owner
uses `allow_messages_and_mentions` and, as owner, can view the document.

Ordinary task recipients continue to require the existing
`user_assign_restrictions`. The owner is the sole exception: when
`allow_task_assignments` is true, any managed non-public user may assign the
owner even without ordinary `ASSIGN` permission.

## 4. Durable data model

### 4.1 MessageConversation

Add an internal `MessageConversation` entity with a deterministic identifier
derived from the two sorted participant User keys. This is a query/index and
state record, not a user-visible chat room.

Store:

- the two participant keys and last-known display-name snapshots;
- `visible_to` participant keys;
- last activity time and last sender;
- a monotonically increasing message sequence and conversation revision;
- per-participant unread count and read-through sequence;
- per-participant cleared-through sequence.

Index it for a cursor query by participant, visibility, and descending last
activity. The Messages sidebar returns 25 conversations at a time.

### 4.2 Message

Store one canonical `Message` child beneath its conversation. Do not create
paired sender/recipient copies.

Store:

- sequence;
- sender and recipient User keys;
- trimmed plain-text body;
- creation timestamp;
- `hidden_for` participant keys;
- the sender-scoped operation identifier used for idempotency.

Limit the body to 1,000 Unicode characters after trimming. Reject an empty
body. Exclude the body from Datastore indexes and all Redis/search/analytics
projections. Do not include message bodies in application logs or exception
context.

Use a deterministic Message key derived from the sender and client operation
identifier. Replaying the same operation and payload returns the original
message; reuse with different recipient/body data is a conflict.

History uses an ancestor query ordered by sequence, with 50 visible messages
per page and an opaque cursor. Query newest-first and reverse only for
chronological display. Apply the participant's cleared-through horizon and
`hidden_for` state while filling the page.

### 4.3 Aggregate Notification

Create one deterministic aggregate Notification beneath each User. Give
ordinary and aggregate Notifications a persisted discriminator so the
aggregate never enters the ordinary cursor query.

The aggregate stores:

- `ordinary_count`: all retained ordinary Notifications;
- `unread_message_count`: unread inbound direct messages only;
- revision/generation data needed to invalidate the browser state.

The badge count is the exact sum of those two counters. The aggregate remains
durable at zero but produces a menu row only when unread messages exist. Its
row reads `1 new message` or `N new messages`, links to `/messages`, and cannot
be individually deleted.

Move Notification create/update/delete/clear behind a focused service that
updates the durable row and aggregate transactionally. An ordinary create or
delete changes `ordinary_count`; a pending/body update changes the revision but
not the count. Clear All deletes only ordinary Notifications and sets their
count to zero.

Upgrade the Redis notification projection to mirror the durable aggregate.
Redis remains disposable: a cache failure cannot roll back a durable mutation,
and a deterministic-key load can repair it without querying Message history.
The existing public `X-Lagniappe-Notification-State` shape may continue to
publish the combined `count`.

### 4.4 Transaction rules

Use bounded, retryable Datastore transactions for direct-message state:

- **send:** create the Message, advance Conversation state, increment the
  recipient's conversation unread count, and increment the recipient's
  aggregate unread count;
- **read:** compare the revision returned by the successful history load, set
  that peer's unread count to zero, and decrement the aggregate by exactly the
  prior peer count;
- **delete received unread:** hide the recipient copy and decrement peer/global
  unread counts once;
- **delete sent or already-read:** hide the actor copy without changing counts;
- **clear peer:** advance only the actor's cleared-through horizon, hide that
  conversation from the actor, and remove any remaining actor unread count;
- **new message after clear:** restore visibility for both participants while
  leaving messages at or below either clear horizon hidden from that user.

Retry transaction-aborted contention using the repository's established
bounded retry pattern. Update Redis only after the durable commit.

The read endpoint must take the Conversation revision returned by the history
response. If a message races the load and changes the revision, return a stale
result and refresh instead of acknowledging a message the user did not see.

## 5. Routes and user interface

### 5.1 Notifications and badge

Keep the current Notifications control permanently present for authenticated
users. Cached HTML renders `...` with an accessible loading/busy label. Once an
authoritative notification state arrives, replace it with the numeric combined
count, including `0`; never hide the control at zero.

Do not add a dedicated prefetch or timer. Existing ping/poll/navigation
responses may resolve the badge through the state header. If they have not,
opening Notifications resolves it. The current non-realtime idle delay is
acceptable.

Change `GET /l/notifications` to return the first 25 ordinary Notifications
plus an opaque continuation cursor and the separately loaded aggregate row.
The performance contract is:

- exactly one bounded ordinary-Notification Datastore query when the menu is
  opened;
- no Message or MessageConversation query;
- Redis reads, a deterministic aggregate key get, and batched target hydration
  are permitted and do not count as additional queries;
- additional ordinary Notification queries happen only when the user chooses
  **Load older**.

For managed users, put **Message a user** first in the dropdown and open a
shared modal. Public users see neither this action nor the Messages page. Clear
All remains an ordinary-notification action and leaves the message aggregate
untouched; hide or disable it when there are no ordinary rows to clear.

### 5.2 Compose modal

The shared compose modal contains:

- a single user facet selector using `permission=message`;
- a plain-text body field with a visible 1,000-character limit;
- a client-generated operation ID;
- submit/cancel controls and an ordinary non-realtime success confirmation.

The same modal is opened from Notifications and from the Messages page. On the
Messages page it is prefilled with the selected eligible peer. There is no
inline composer at the bottom of history.

### 5.3 Messages page and endpoints

Add a managed-user-only Messages entry to the authenticated directory and a
single `/messages` page. Use a responsive sidebar pattern: persistent peer list
on desktop and a selector on narrow screens.

Suggested interfaces:

- `GET /messages?with=<conversation>` — page shell and route state;
- `GET /l/messages/conversations?cursor=...` — 25-peer sidebar page;
- `GET /l/messages/conversations/<id>?cursor=...` — 50-message history page;
- `POST /l/messages` — send `{recipient, body, operation_id}`;
- `POST /l/messages/conversations/<id>/read` — acknowledge a loaded revision;
- `DELETE /l/messages/<message-key>` — hide the actor's copy;
- `DELETE /l/messages/conversations/<id>` — clear the actor's peer history.

Default to the newest conversation with unread messages, otherwise the most
recent conversation. The aggregate Notification link follows the same rule.
Opening the Notifications dropdown alone never marks direct messages read.

All conversation/history/delete routes authorize by participant membership.
The site owner has no override for conversations they do not participate in.

## 6. Task assignment notifications

Keep the existing assignment selector and `permission=assign` cache path. The
owner projection augments that search only when `allow_task_assignments` is
true and the typed query occurs in the owner's name.

Render the assignment control when:

- ordinary assignment restrictions permit candidates;
- the owner exception is enabled; or
- an existing assignee must be displayed as a preload.

The task mutation must validate the submitted assignee against the current
assignment restriction or the canonical owner exception. Do not rely solely on
the presence of a client-side option.

Create an ordinary Notification only when a durable task mutation changes the
assignee to a different non-self user. Do not notify for an unchanged assignee,
unassignment, or self-assignment. A later unassign/reassign is a new transition
and should notify again.

Use a durable assignment revision/event identifier so offline retries and
duplicate requests cannot produce duplicate Notifications. Put this detection
at the task mutation/service boundary so every task create/update path behaves
consistently. Target the Task and use server-generated plain text such as
`Alice assigned you a task.` Assignment notices do not enter Message history.

Do not create notices for tasks already assigned before the feature is enabled.

## 7. Document mentions

Limit the first version to the main collaborative document on Page and Project
entities.

Add a Tiptap/Yjs mention node activated by `@`. Its suggestion menu uses the
cached contextual user search (`permission=mention` plus the document key).
Normal candidates must satisfy message eligibility and document `VIEW` access.
The owner additionally requires `allow_messages_and_mentions` and an
owner-name query match.

Persist internal mention-node attributes for:

- a random occurrence UUID;
- recipient User key;
- display-name snapshot.

Queue newly inserted occurrences with the existing sync/offline record. After
an accepted durable checkpoint, the server must verify that the occurrence is
still present in the saved HTML, the actor is allowed to mention the recipient,
and the recipient can still view the document. Only then create an ordinary
Notification targeted at the Page or Project, such as
`Alice mentioned you.`

Keep a small durable idempotency marker keyed by document and occurrence UUID.
It must survive deletion/Clear All of the visible Notification so a replay or
later checkpoint cannot redeliver the mention.

- Removing the mention before its first durable checkpoint sends nothing.
- Removing it after delivery does not retract the historical Notification.
- Re-inserting a user creates a new occurrence and may notify again.
- Retry/offline replay of one occurrence creates at most one Notification.

Internal rendering may style the mention. Public document responses and HTML
site exports must replace it with plain `@Display Name` text and remove the
recipient key, occurrence UUID, and all mention-specific data attributes.

## 8. Deletion, retention, and privacy

- A participant may hide one Message or clear their own history with one peer;
  neither action changes the other participant's copy.
- When both participants can no longer see a Message, it may be physically
  compacted. Correct behavior must not depend on immediate compaction.
- If one User is deleted, preserve the remaining participant's history, retain
  the last-known name, mark the peer as deleted, and disable compose.
- If neither participant remains, purge the conversation and its messages.
- Permission/group loss does not erase existing participant history.
- Direct-message bodies are visible only to participants. Do not add owner
  audit access, moderation search, site-export inclusion, or global indexing in
  v1.
- No automatic expiration is required in v1. Revisit retention and abuse
  controls if usage demonstrates a need.

## 9. Migration and delivery sequence

Implement in independently reviewable stages:

1. **Foundation**
   - add owner fields and shared projection;
   - add cached message restrictions and owner search behavior;
   - add Message/MessageConversation contracts and indexes;
   - add the aggregate Notification and transaction-aware notification service;
   - backfill the ordinary discriminator and aggregate counts;
   - bump/repair the Redis notification projection schema.
2. **Direct messages**
   - add send/read/delete/clear services and routes;
   - add the shared compose modal and centralized Messages page;
   - update the Notifications menu, pagination, and permanent badge.
3. **Assignments**
   - harden assignee authorization;
   - add idempotent task-assignment Notifications.
4. **Mentions**
   - add the editor node and cache-backed selector;
   - carry occurrence data through checkpoint/offline replay;
   - add the delivery ledger and public-output sanitization.

Deploy required Datastore indexes before enabling reads that depend on them.
Run the Notification backfill before switching the menu to the discriminator
query. The migration must be resumable and safe to rerun. User owner flags need
no backfill because absent values deliberately mean `false`.

The durable per-user aggregate is an acceptable v1 coordination point for this
low-volume feature. If measured contention becomes material, preserve the
external contracts and replace it with sharded/asynchronous aggregation later.

## 10. Verification and acceptance criteria

Before adding or materially reshaping tests, follow
`documentation/TESTING_WRITING_TESTS.md`. Add source annotations and run
traceability/template-contract checks required by repository policy.

### Unit coverage

- message restriction union, global access, self exclusion, and exact
  commit-time predicate;
- public-user cache absence and direct-key rejection;
- owner defaults, owner-only updates, cache repair/invalidation, normal-result
  removal, and conditional reinsertion;
- owner search matching for case-insensitive interior substrings, blank and
  nonmatching queries, deduplication, and preload behavior;
- deterministic conversation/message keys and operation conflicts;
- transaction retry/idempotency and all unread/global-count transitions;
- one-sided delete, clear horizon, new-after-clear, and deleted-peer behavior;
- aggregate Notification backfill, Redis schema repair, and ordinary count;
- task assignment transition/retry behavior;
- mention eligibility, saved-occurrence validation, and delivery-ledger
  idempotency;
- public mention sanitization.

### JavaScript coverage

- permanent Notifications control and `...` to `0`/count resolution;
- no new badge prefetch or periodic poll;
- compose action/modal, validation, operation ID, and prefilled peer;
- aggregate row, ordinary Clear All, and Load older behavior;
- responsive peer selection, cursors, history ordering, read race refresh,
  per-copy delete, and clear-history confirmation;
- `@` menu keyboard/mouse behavior and pending mention offline replay.

### E2E coverage

- send, receive, peer history, aggregate count, acknowledgement, delete, clear,
  and new-message-after-clear flows;
- multiple peers and both conversation/message cursor boundaries;
- same-group, viewable-group, global Users, owner toggle/query, group-loss,
  deleted-peer, self, and public-user cases;
- participant-only history, including denial to a nonparticipant owner;
- task create/update/reassign/unassign/self and crafted-assignee requests;
- mention save, remove-before-save, retry, offline replay, reinsert, document
  access loss, and owner toggle;
- public page and HTML export output containing plain mention text and no
  internal identifiers.

### Performance acceptance

Instrument the Notifications-open request and prove:

- one ordinary Notification ancestor query with a limit of 25;
- zero Message or MessageConversation queries;
- no per-row Datastore query pattern;
- an exact combined badge after resolution;
- message count/list correctness after Redis eviction and repair.

Run focused real test paths first. Expand to the relevant unit and JavaScript
suites, then run E2E files sequentially against the managed test server. Finish
with:

```text
venv/bin/python run.py template-contracts
venv/bin/python run.py traceability --changed --check
```

## 11. Expansion points deliberately left open

The data model can later support attachments, moderation tooling, explicit
retention, notification delivery channels, or realtime transport without
changing the first-version participant/history contracts. None of those should
be implemented until a concrete use case and privacy policy justify the added
scope.
